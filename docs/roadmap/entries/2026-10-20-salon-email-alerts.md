- 🟢 **Alertes salon par e-mail : quand aucune notification de l'app MyWeli Pro ne parvient à un membre, un e-mail ; « Alertes par e-mail » sur le web Pro ; en ligne (#649 ; le serveur en production ; backend + web, 2026-10-20).** ([salon-email-alerts.md](../../design/salon-email-alerts.md)) **Le manque** (audit de parité §3 n° 5) : le serveur ne prévenait un salon que par push de l'app ; un salon qui n'utilise que le web n'apprenait rien onglet fermé — ni la demande à accepter, ni l'annulation. **Ce qui change** : pour chaque destinataire (la règle du push : l'équipe qui voit tout le planning, le Collaborateur pour ses rendez-vous), si aucun push n'est accepté — pas d'appareil, push coupé, FCM qui refuse — et que sa préférence `emailAlerts` est active (par défaut, migration `0039`), un e-mail à l'adresse de son adhésion : la phrase du push, ce qu'il y a à faire, le lien vers la fiche sur le web dans le bon salon ; aucune donnée client, le nom du salon échappé, budget « warm », un envoi qui échoue n'arrête ni le fil ni le membre suivant. Un membre que l'app atteint ne reçoit jamais les deux. Web Pro : la section « Préférences » sous les notifications, l'interrupteur du web client déplacé dans un composant partagé, un BFF qui ne transmet que `emailAlerts` ; la FAQ de `/professionnels` le dit. **Décisions du propriétaire** : les e-mails et l'interrupteur tels qu'écrits, actif par défaut, la phrase de la FAQ ; la notification du navigateur en tranche à part. **Trouvé en construisant** : l'e-mail défilait de côté sur téléphone (le cadre fixe des avis d'abonnement — qui ont le même défaut) ; la référence de menace du notifier était fausse (T58, pas T25). **Gardes** : rouges d'abord, 15 mutations vues rouges (backend, web, e2e) ; 1 779 + 85 Postgres backend, 1 659 web, 132 e2e. **Reste** : déployer le serveur avant le web ; vérifier le quota du plan Resend ; un vrai envoi. **Dépend de** #642.
