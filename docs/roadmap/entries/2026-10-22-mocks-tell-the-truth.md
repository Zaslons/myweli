- 🟢 **Les doublures se comportent comme le serveur : les limites d'invitation, le salon neuf, le catalogue du salon courant, des identifiants uniques (app, 2026-10-22).** ([hygiene-batch9.md](../../design/hygiene-batch9.md) §10) Le lot 9 du [BACKLOG](../../BACKLOG.md), PR B (B9.6, décision 35).
  - **Avant** : la limite d'invitations du faux était un compteur par instance, jamais remis à zéro, commun à tous les salons et adresses ; un salon né dans le faux copiait Salon Excellence (ses prestations, ses photos, sa note, son acompte de 30 %) ; les écritures du catalogue répondaient « succès » sans rien garder, et celles des employés et des membres cherchaient dans tous les salons ; sous l'horloge gelée, deux invitations avaient le même id.
  - **Ce qui change** : les deux seaux du serveur par jour UTC (20 par salon, 3 par adresse, alias compris) ; un salon neuf vide et à 0 % ; le catalogue gardé là où le client le lit, dans le salon où la session agit, avec les `forbidden` et `not_found` du serveur ; un compteur d'identifiants. Rien n'attend 0.0.2 : les builds du store parlent au serveur (`useApiBackend`) ; seuls les tests et le mode maquette se servent des doublures.
  - **À suivre** : PR C (les formulaires prouvés, B9.7).
