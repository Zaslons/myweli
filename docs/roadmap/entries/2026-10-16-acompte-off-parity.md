- 🟢 **Acompte — désactiver les acomptes n'efface plus l'opérateur ni le pourcentage, et 0 % veut dire « pas encore choisi » (web + app, 2026-10-16).** ([acompte-off-parity.md](../../design/acompte-off-parity.md)) **Le défaut** : `PUT /providers/{id}/deposit-policy` remplace la politique entière, et le web envoyait `mobileMoneyOperator: null` et `depositPercentage: 0` dès que l'interrupteur était sur « non » — l'opérateur et le pourcentage étaient effacés. Or la lecture d'un rendez-vous sert l'opérateur **actuel** du salon : un client qui devait encore son acompte perdait le nom de l'opérateur et le lien « Payer avec Wave ». L'app, elle, envoie ce qu'elle tient. **Le 0 %** : tout nouveau salon est créé à 0 % (et le web en écrivait d'autres) ; l'app affichait « 0 % » avec le curseur dessiné à 5 %, et activer puis enregistrer était refusé — « Informations invalides. ». Décision du propriétaire : 0 % = pas encore choisi, les deux formulaires proposent 30 % (`kDefaultDepositPercentage` ↔ `DEFAULT_DEPOSIT_PERCENT`, gardés d'accord par un test croisé) ; aucune migration, aucun changement serveur. **Web, en plus** : un chargement raté (403, 5xx, coupure) affichait un formulaire vierge dont l'enregistrement écrasait la vraie politique — c'est l'`ErrorState` et « Réessayer », comme l'app ; un enregistrement sans réseau laissait « Enregistrer » désactivé pour toujours ; le champ refuse sous 1 % comme son message le dit ; un pourcentage choisi est relu au centième, pour qu'un enregistrement intouché réécrive ce qu'il a lu. **Vu rouge** : chaque test d'abord contre l'ancien code ou sous mutation ; 9 mutations sur 9 rattrapées dans la passe finale ; l'e2e (désactivé → enregistré → rechargé → réactivé) rouge sous le D1 d'origine. **Hors périmètre, consigné** (§7) : les plages 5–80 % (app) / 1–100 % (web) ; l'étape « Acompte » de l'accueil Pro qui se coche pour tout salon ; 14 autres écrans web Pro qui tournent pour toujours sur une coupure réseau. **Déploiement** : le web au merge ; l'app au prochain build ; rien côté serveur.
