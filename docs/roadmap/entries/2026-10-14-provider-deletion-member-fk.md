- 🟡 **Supprimer un compte Pro aboutit à nouveau : la ligne d'équipe ne retient plus l'identité ; reste la CI, la fusion, puis le déploiement en production (backend, 2026-10-14).** Trouvé par le propriétaire pendant les vérifications du build 587, avant « Submit for Review » : un compte Pro neuf, « Supprimer » → « Une erreur est survenue ». **Le défaut, vérifié** : trois `DELETE /me/provider` en 500 `ForeignKeyViolationException` à 20:06, 20:07 et 20:10 UTC (révision `myweli-api-00037-zzq`) ; en 60 jours, aucune suppression de compte Pro n'a abouti. Le service *révoquait* les lignes `provider_members` du compte — un UPDATE qui garde `account_id` — puis supprimait l'identité, que `provider_members.account_id` référence **sans action ON DELETE** (0027). Tout propriétaire de salon est touché, depuis le 2026-07-12 (#222). Aucun test ne pouvait le voir : toutes les suppressions tournaient sur les jumeaux en mémoire, sans clés étrangères. **Le correctif** ([backend-provider-deletion-member-fk.md](../../design/backend-provider-deletion-member-fk.md)) : migration **0038** (la clé passe en `ON DELETE CASCADE`, dans une seule transaction, sûre au retour arrière) ; les lignes d'équipe sont **supprimées**, plus révoquées (`deleteAllForAccount`, les deux jumeaux) ; les quatre `DELETE` de l'identité tiennent **dans une transaction** — avant, sessions et codes partaient avant l'instruction qui échouait. **Trois tests Postgres, vus rouges sur le code d'avant** : le chemin de production de bout en bout (rouge avec l'erreur exacte de la production, 23503 `provider_members_account_id_fkey`), aucune clé étrangère vers une identité ne bloque son effacement (rouge : exactement `provider_members.account_id → provider_users: a`), une suppression qui échoue ne touche pas aux sessions (rouge : 0 sur 1). Suite backend complète sur une base neuve : 1 740 réussis, 2 ignorés, 0 échec ; 0038 appliquée aussi sur une base portant l'ancienne clé — une seule clé, en cascade. **Aucun changement d'app ni de contrat.** **Reste** : CI, fusion et déploiement, chacun sur le mot du propriétaire ; puis le propriétaire relance « Supprimer » sur le compte qui a échoué (d'après le code, il se reconnecte en propriétaire — non observé), et seulement ensuite « Submit for Review ».
