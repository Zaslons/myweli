- 🟡 **Web Pro — les horaires en plusieurs plages et les dates bloquées en lot, comme dans l'app ; et la page ne plante plus sur une date bloquée depuis l'app ; fusionné (#646) : le web en ligne ; l'app part avec 0.0.2 (web + app Pro, 2026-10-19).** ([web-pro-availability-ranges.md](../../design/web-pro-availability-ranges.md)) L'audit de parité (P1) l'avait relevé, le code l'a confirmé : le web ne montrait et n'éditait que **la première plage** de chaque jour (les suivantes portées invisibles à l'enregistrement) — un salon fermé à midi voyait son matin et rien d'autre ; les dates se bloquaient une à une, le passé accepté, sans confirmation. **Trouvé en route, plus grave** : l'app écrit une date bloquée comme un instant (minuit du salon en UTC), le web la formatait en y collant « T12:00:00.000Z » → « Invalid time value » → **la page Disponibilités ne s'ouvrait plus** pour un salon qui avait bloqué une date depuis l'app. **Maintenant** : chaque plage à l'écran (« Retirer », « Ajouter une plage » — une heure après la précédente, quatre heures —, « Copier sur les autres jours » qui copie toutes les plages, l'aide « Fermé à midi ? Ajoutez une deuxième plage. ») ; deux plages qui se chevauchent sont refusées (« Lundi : deux plages se chevauchent. ») — **sur le web et dans l'app**, à la demande du propriétaire ; les dates comme l'app : « Gérer les dates bloquées » → un calendrier d'aujourd'hui à un an, sélection multiple, le résumé vivant de l'app → la confirmation qui nomme le sens → l'écriture **des seules dates** (une modification d'horaires non enregistrée n'est ni écrite ni perdue) ; « Débloquer » par ligne, confirmé. Les deux formats se lisent comme un jour du salon ; les entrées non touchées repartent à l'identique, les nouvelles au format de l'app. Pauses et horaires d'employé restent à une plage, comme l'app. **Vu rouge d'abord** (44 web, 2 app) ; **vérifié dans le navigateur** de bout en bout ; 1 607 tests web, `flutter analyze` 0. Web au merge ; l'app au prochain build Pro.
