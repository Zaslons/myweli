- 🟢 **La spec du compte de démonstration pour la revue des stores — écrite avant le code (docs, 2026-08-26).** C'est le plus gros morceau d'ingénierie du chemin « Pro d'abord » (mobile-external-testing.md §5.2) : l'app Pro s'ouvre sur `/pro/login`, un relecteur sans identifiants ne voit **rien**, et aucune des trois méthodes ne se donne — Google/Apple crée un compte neuf (l'entonnoir d'inscription, pas un tableau de bord) et le code e-mail part vers une adresse que nous contrôlons. Play exige en plus des identifiants **réutilisables qui contournent les codes à usage unique**. **Le renversement qui structure la spec : l'identifiant sera imprimé dans les notes de revue des deux consoles — il est public par conception.** Rotation, verrouillage et force brute deviennent secondaires ; on suppose que tout le monde a le code, et on borne ce qu'il ouvre. **Concevoir la pièce, pas la serrure.** La pièce : identité en **constante de compilation** `revue@myweli.test` — TLD réservé RFC 2606, structurellement incapable d'être une vraie personne, aucune erreur de configuration ne peut l'élargir (l'argument du seam Q1b, promu) ; code fixe à 6 chiffres (le champ de l'app exige exactement 6 — vérifié dans `validators.dart` des deux côtés) en Secret Manager, **non défini → seam absent**, ce qui est l'interrupteur d'arrêt. **Zéro changement d'app, zéro nouveau endpoint, zéro migration** : le seam modifie le comportement de trois routes existantes pour exactement une identité, et le compte est une ligne ordinaire créée **via le vrai produit** — pas de script de seed, le provisionnement est lui-même une répétition du parcours d'intégration d'un salon. **Deux capacités soustraites, aucune ajoutée** : publier (403 `demo_account_locked`, vérifié sur l'e-mail du propriétaire dans le service — le salon démo ne peut jamais apparaître sur myweli.com ni déclencher la reconstruction fraîchement câblée) et inviter l'équipe (le seul canal qui envoie du courrier à un tiers arbitraire depuis une session authentifiée — un identifiant public ne doit pas devenir un canon à courriels). Tout le reste marche : le tableau de bord est pleinement fonctionnel sur un salon **draft**, par conception (T51), donc le bac à sable ne coûte rien au relecteur. **Et une erreur attrapée en écrivant la spec, pas en la relisant** : le premier jet plaçait le refus d'envoi `.test` dans `ResendEmailProvider` — la mauvaise couche, le budget étant déjà réservé par l'enveloppe `BudgetedEmailProvider` avant la délégation ; vérifié contre `email_provider.dart` avant publication, et la correction est consignée dans la spec elle-même. L'app consommateur n'a besoin d'**aucun** seam : navigable déconnectée, un relecteur peut utiliser Google/Apple tel quel. Menace **T69** au modèle ; questions ouvertes : cadence de remise à zéro, cosmétique d'expiration d'essai, formulation du formulaire App access. Spec **Draft** — alignement avant toute ligne de code.
