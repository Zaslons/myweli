- 🟢 **La file d'attente de fusion ne peut pas être activée ici : le dépôt appartient à un compte personnel (CI, 2026-08-24).** L'entrée précédente annonçait que le déclencheur `merge_group` était posé « avant » d'activer la file. Le déclencheur est bien en place et reste correct — mais **l'activation est impossible sur ce dépôt**, et l'annonce était donc fausse. GitHub réserve la file d'attente aux dépôts détenus par une **organisation** ; `Zaslons/myweli` appartient à un **utilisateur**, public ou non. Le type de règle `MERGE_QUEUE` existe pourtant dans le schéma GraphQL global — ce qui rend l'échec trompeur : l'énumération résout, et c'est l'API REST qui refuse la création avec un `Invalid rule 'merge_queue'` sans plus d'explication. Trois formes de charge utile ont été essayées, dont celle de la documentation mot pour mot, avant que l'introspection ne montre que le problème n'était pas la syntaxe. **Rien n'a été modifié** : zéro ruleset créé, protection de `main` intacte (`strict`, 10 contrôles, `enforce_admins`). **Ce qui reste vrai et acquis** : le déclencheur `merge_group` dans `ci.yml` est inoffensif tant qu'aucune file n'existe, et deviendra nécessaire le jour où le dépôt passe en organisation — la garde qui l'asserte reste utile, et elle assertera aussi tout futur workflow produisant un contrôle requis. **Et la moitié qui comptait le plus a bien atterri** : les entrées de journal sont désormais un fichier par changement, donc les rebases ne peuvent plus entrer en conflit — c'était la source des neuf conflits d'affilée et des deux résolutions qui ont commité les marqueurs. **La leçon est celle de la journée, appliquée à moi** : j'ai annoncé une capacité avant de vérifier qu'elle existait, exactement le défaut que ce dépôt documente sous « dire ce qu'on a vérifié, pas ce qu'on croit ».
