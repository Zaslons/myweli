- 🟢 **Les erreurs de l'API portent les en-têtes CORS (backend, 2026-10-15).** **Le défaut, vu sur un vrai serveur** : la chaîne racine plaçait l'observabilité *à l'extérieur* de CORS ; quand un handler levait, CORS n'avait rien à décorer, et le 500 — comme le 400 du contrôle des requêtes, lui aussi hors de CORS — partait sans `access-control-allow-origin`. Pour la console d'administration, le seul client navigateur qui appelle l'API directement, une erreur serveur devenait une « erreur réseau » opaque. Le commentaire au-dessus de la chaîne donnait cette raison pour l'ordre qu'il n'appliquait pas. **Le correctif** ([backend-cors-error-responses.md](../../design/backend-cors-error-responses.md)) : CORS devient la couche la plus extérieure — toute réponse à une origine autorisée, erreur comprise, porte les en-têtes ; une origine hostile n'en reçoit toujours aucun — et `X-Request-Id` est exposé, pour qu'un écran d'erreur puisse montrer l'identifiant à citer. **Vu rouge** : le nouveau test contre l'ancien ordre (3 échecs) ; la sonde, lancée sur le serveur compilé, ne trouvait aucun en-tête sur l'ancienne chaîne et les trouve sur la nouvelle. Elle tourne désormais dans le boot smoke de la CI.
