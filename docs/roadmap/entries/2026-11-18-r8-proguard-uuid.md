- 🟡 **Android : R8 écrit en clair dans la build de publication, et chaque bundle nomme son fichier de correspondance pour Sentry (app · 2026-11-18 — BACKLOG B0.10, décisions 112 et 135).** Non fusionné : branche `chore/r8-proguard-uuid`, créée depuis `main` (`191e1123`). L’étape 3 (e) de [android-play-release.md](../../design/android-play-release.md) §4, avant la PR A de B0.17.
  - **Pourquoi :** R8, l’outil qui réduit et renomme le code Java et Kotlin d’une build Android, tourne déjà sur chaque build de publication : le plugin Gradle de Flutter l’allume. Mais `app/build.gradle.kts` disait le contraire, dans un commentaire, et rien ne nommait le fichier de correspondance (`mapping.txt`) d’une build. Un plantage dans un plugin ou dans le code Java du moteur arrivait donc dans Sentry avec des noms illisibles.
  - **Ce qui change :** `isMinifyEnabled = true` et `isShrinkResources = true` sont écrits dans le bloc `release`, à la place du commentaire faux. `tool/release_build.sh` donne à chaque build Android un identifiant (UUID) propre, passé à l’app ; il efface d’abord l’ancien `mapping.txt`, refuse une build qui n’en laisse pas (le bundle est renommé `.refused`) et imprime, en dernier, la commande `sentry-cli upload-proguard` qui range le fichier sous cet identifiant. L’app transmet l’identifiant à Sentry ; sans lui, la valeur reste vide (`null`), jamais une chaîne vide. L’iPhone ne reçoit rien de tout cela.
  - **Les garde-fous :** un nouveau test lit le fichier Gradle, commentaires retirés ; sept cas lancent le vrai script dans un dépôt jetable ; trois cas tiennent le réglage de Sentry. Chaque nouveau cas a d’abord échoué sur l’ancien code, puis chaque mutation (une ligne effacée, `false`, un identifiant écrit en dur, le contrôle retiré…) l’a fait échouer à nouveau.
  - **Reste :** la build Android réelle (étape 5) montrera le fichier dans le bundle et si Sentry enregistre l’identifiant ; un vrai plantage Java le montrera dans Sentry (§5, ligne 17).
