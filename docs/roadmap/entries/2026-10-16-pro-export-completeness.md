- 🟢 **L'export des données du salon refuse au lieu de livrer un fichier à trous — une lecture en échec ne devient plus une section vide, le fichier clients dépasse 20, l'export est au propriétaire comme dans l'app, et la liste clients a enfin un ordre total (web Pro + backend, 2026-10-16).** [web-pro-export-completeness.md](../../design/web-pro-export-completeness.md). **Vérifié dans le code avant d'y toucher** : `CompteDangerSection` lançait les trois lectures (rendez-vous, clients, revenus) sans lire un seul statut, et chaque aide de `lib/api/pro.ts` change un non-200 en « rien » — le salon recevait `"clients": []` ou `"earnings": null`, présentés comme ses données complètes ; un `fetch` qui lève laissait le bouton sur « Préparation… » jusqu'au rechargement ; le fichier clients s'arrêtait à la première page (20, le défaut du serveur) sans le dire ; et le web offrait l'export au Gérant (`profile.manage`) quand l'app ne l'offre qu'au propriétaire (`salon.publish`, R4b) — un Gérant n'a pas `finances.view`, sa lecture des revenus répondait 403 à chaque fois. **Décisions du propriétaire** : refuser plutôt que marquer une « section indisponible » (le lecteur est un gérant de salon, pas un développeur ; l'app refuse déjà) ; propriétaire seul, comme l'app, R5 §6 et T39 ; et le départage du tri dans le même changement. **Désormais** : une lecture qui échoue ne produit ni fichier ni copie, la section dit ce qui manque (« Export interrompu : impossible de charger le fichier clients. Aucun fichier n'a été créé. Réessayez. ») et les boutons servent de nouvel essai ; un 401 mène à la connexion ; un presse-papiers refusé renvoie vers le téléchargement. Le fichier clients est parcouru page par page (50, le maximum du serveur) et refusé si le parcours ne tombe pas juste (un `total` qui bouge, un identifiant vu deux fois). **Backend** : la liste clients triait par `last_visit_at DESC NULLS LAST, created_at DESC` sans clé unique — or la migration 0024 a créé ses fiches dans une seule transaction, donc avec le même `created_at` ; Postgres a rendu des ex æquo dans un autre ordre selon le `LIMIT` (vu : `t3, t5` pour une page de 2 quand l'ordre du tas était `t5, t3`). `id` devient la dernière clé, dans Postgres et dans le jumeau en mémoire — qui, lui, ignorait même `created_at`. La « page suivante » de l'écran Clients avait le même défaut. **Vu rouge** : chacun des 10 tests d'export contre l'ancien code (pas d'alerte, un fichier quand même, « Copié ✓ » après un échec, deux rejets non gérés, 50 clients sur 120), le Gérant (bouton présent), les deux tests de l'ordre en mémoire et celui sur Postgres. **Pas dans ce changement** : l'export de l'app (quatre lectures sur cinq retombent encore sur une liste vide, et les clients s'arrêtent à la page 1) et l'export consommateur. **Déploiement : le serveur d'abord.** D'ici là, un salon aux fiches ex æquo peut voir l'export refusé pour « le fichier clients ».
