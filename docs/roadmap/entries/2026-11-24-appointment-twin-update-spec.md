- 🟡 **Spec : le double de test du dépôt des rendez-vous n’écrit plus que ce que Postgres écrit (backend · documentation · 2026-11-24).** Branche `docs/appointment-twin-update-spec`, créée depuis `main`. Spec : [appointment-twin-update.md](../../design/appointment-twin-update.md). Documentation seule : aucun code avant les réponses.
  - **Le défaut :** en test, le double en mémoire du dépôt des rendez-vous accepte n’importe quelle clé et n’importe quelle valeur dans une mise à jour. Postgres n’écrit que six clés, ignore le reste sans rien dire et refuse certaines valeurs. Un test de service peut donc passer pour un code que la production casserait : c’est ainsi que la devise d’un rendez-vous n’a jamais été enregistrée (lot 14).
  - **Prouvé, pas supposé :** une sonde jetable, sur une base locale supprimée après, a passé la même mise à jour aux deux doubles.
    - Le double en mémoire garde six clés que Postgres ignore ; la clé témoin, `status`, change des deux côtés.
    - Il rend aussi ses propres objets : un appelant qui les modifie modifie ce qui est stocké. Deux endroits du code de production contournent déjà ce piège, et le disent.
  - **Ce que propose la spec :**
    - une seule liste des six clés, lue par les deux doubles ;
    - une clé hors liste, ou une valeur que Postgres refuserait, refusée des deux côtés, avant toute écriture ;
    - un déplacement dédié pour le changement de téléphone d’un invité, le seul appelant qui s’appuyait sur la brèche ;
    - des copies à chaque lecture, dans la forme que rend Postgres (sans `endsAt`, que Postgres écrit mais ne relit jamais) ;
    - le contrat qui tient les deux doubles, rouge d’abord, et dix mutations.
  - **Aucun changement pour les utilisateurs :** aucun appelant de production ne passe une clé hors des six ni une valeur refusée.
  - **Relue une fois par un lecteur indépendant, chargé de la réfuter :** un bloquant (`endsAt`, qui rendait faux un test annoncé vert), cinq constats à corriger et trois détails, tous intégrés (§13).
  - **Trouvé à côté :** BACKEND.md disait que la CI n’exécute jamais les suites Postgres. Elle les exécute depuis B3c (juin) ; la phrase était fausse dès son écriture. Elle est corrigée dans cette PR ; la même phrase dans un fichier de test le sera par la PR de construction.
  - **Approuvée le 2026-11-24 :** les cinq réponses d’un coup, « Approve as recommended », décisions 214–218 dans le BACKLOG, regroupées dans un nouveau lot 15 (B15.1).
  - **Reste, sur le mot du propriétaire :** la fusion de cette PR, puis la construction de B15.1 dans sa propre PR. Elle n’a pas de déploiement à elle : elle part avec le prochain déploiement du backend.
