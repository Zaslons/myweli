- 🟡 **Le deuxième refus d’Apple sur la 0.0.1 : le lien de la connexion, le film et les notes (app Pro + web + publication · 2026-11-03).** Non fusionné ; rien n’est en ligne, construit, collé ni envoyé. ([app-review-round-2.md](../../design/app-review-round-2.md) ; [BACKLOG](../../BACKLOG.md) B0.16, décisions 71–76)
  - **Avant** : Apple a refusé le build 698 le 3 novembre, sur un iPad Air. Sous 2.3.4 : « Includes framing around the video screen capture of the app. » Sous 3.1.1 : « S’inscrire sur myweli.com » sur la connexion, avec « any other links to your site » en plus. Nos notes citaient 3.1.3(f), dont le texte est une liste fermée (VoIP, stockage, e-mail, hébergement web), et envoyaient le relecteur s’inscrire sur le site.
  - **L’app** : le lien quitte la connexion, sur les deux plateformes, sans phrase de remplacement. Un garde-fou lit la fermeture d’imports de Pro : les pages de notre site que l’app ouvre sont exactement cinq, et une sixième fait échouer le test.
  - **Le web** : ces cinq pages (`/support`, `/politique-confidentialite`, `/cgu`, `/mentions-legales`, `/suppression-compte`) perdent « Espace pro » et le groupe des salons, dans le HTML et pas seulement à l’écran. `/support` ne parle plus de facturation. Toutes les autres pages gardent leurs liens.
  - **Le film** : la coupe plein écran des mêmes prises, dans les deux emplacements iPhone. **Risque accepté par le propriétaire** : elle finit toujours sur une carte papier, et Revenus dit « Total » où l’app dit « Total réalisé ». `film.frame` le dit, donc l’outil reproduit ce fichier : 22 octets diffèrent, et les 862 images se décodent à l’identique (ffmpeg et AVFoundation). La reprise propre, sur de nouvelles prises et sans carte de fin, est pour la 0.0.2.
  - **Les textes** : des notes sans 3.1.3(f) ni consigne d’inscription (3 865 octets), la description avec ses deux changements (1 061 caractères), l’URL marketing laissée vide, une réponse pour le Resolution Center, un « What to Test », et le contrôle de l’IPA retourné : le relevé du 698 exigeait le lien présent, celui-ci l’exige absent. **La formulation attend l’accord du propriétaire, et lui seul envoie la réponse.**
  - **Vu rouge** (le détail : les messages de commit) : l’app, 18 échecs sur l’ancien code et 48 mutations ; le web, 44 échecs sur l’ancien habillage et 72 mutations ; le film, sa ligne `film.frame`, 2 mutations ; les textes, 7 garde-fous sur 8 rouges sur les anciens documents (le huitième relit des libellés qui étaient justes, et il rougit sous mutation), puis 28 mutations et un témoin qui reste vert. **Trouvé en lançant les tests** : un garde-fou tenait la description de Play mot pour mot à celle de l’App Store. Play garde son texte, le test n’admet que ces deux changements, et le propriétaire dira si Play les reprend.
  - **Lu dans un vrai binaire** : le contrôle de l’IPA affiche `OK` sur un build non signé de cette branche, qui ne nomme de notre site que les cinq pages, et `ÉCHEC` sur le binaire du 587 et sur des fichiers écrits exprès. Ce n’est pas encore l’IPA signée.
  - **Non observable d’ici** : l’état d’App Store Connect, le fil du Resolution Center, l’app sur un appareil, et ce que fera le relecteur. Le web n’a été lu qu’en local : la vraie lecture vient après la fusion (spec §12, étape 2).
  - **À suivre, dans l’ordre** : l’accord sur les notes ; la PR et la fusion, qui met le web en ligne ; la relecture des cinq pages ; le build, l’IPA, l’envoi ; la passe ciblée sur l’appareil, iPad compris, et une session de plus de 15 minutes ; le film dans les deux tailles, relu dans « View All Sizes in Media Manager » ; la description, le build, les notes ; la réponse et « Add for Review », par le propriétaire. Pas de déploiement du backend (décision 47).
