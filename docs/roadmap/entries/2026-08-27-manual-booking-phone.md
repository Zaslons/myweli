- 🟢 **Une réservation manuelle avec téléphone ne pouvait JAMAIS réussir — le formulaire interdisait physiquement le format que le serveur exige (app + web + backend-test, 2026-08-27).** Signalé par le propriétaire : « Création impossible » en ajoutant un numéro. Vérifié avant de corriger, et le mécanisme est triple pour une seule cause racine — aucune normalisation E.164 aux deux frontières de formulaire, alors que le contrat (`openapi.yaml`, `clientPhone: E.164`) et le serveur (`isValidE164`, 400 `invalid_phone`) sont corrects et inchangés. **App** : un hint « +225 … » au-dessus d'un formateur `digitsOnly` (le `+` intapable), jugé par une règle 10-chiffres-locaux, envoyé brut — l'état acceptant du validateur client était un rejet serveur garanti ; et le pré-remplissage depuis la fiche client rejetait les numéros stockés de l'app elle-même (+225… = 13 chiffres ≠ 10). **Web** : zéro validation, et le 400 tombait dans le `default` de `conflictMessage` → « Création impossible. Réessayez. » — une invitation à réessayer ce qui ne peut pas réussir. **Le correctif n'invente rien** : les deux plateformes possédaient déjà le bon champ (`PhoneNumberField` / `PhoneField`, libphonenumber, CI par défaut, émet l'E.164 — sept autres formulaires s'en servent) ; les formulaires de réservation manuelle étaient les deux seuls retardataires. Blocage à la soumission avec faute sous le champ, et `invalid_phone` nommé des deux côtés — « Numéro invalide (format international, ex. +2250700000000). », le français du modal « Ajouter un client », au caractère près (parité pinnée). Pourquoi 3 500 tests verts n'ont rien vu : chacun fournissait un E.164 pré-formé à une couche sous le formulaire ; les nouveaux tests tapent dans le VRAI widget et affirment ce que le service reçoit — plus le négatif réaliste côté serveur (`'0708091011'` → 400). Neuf mutations regardées rouges. La moitié app atteint les téléphones au prochain envoi Play (531+) ; web en ligne au merge.
