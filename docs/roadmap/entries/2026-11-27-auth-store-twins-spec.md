- 🟡 **Spec : les magasins de connexion d’accord avec Postgres, et le lien Google ou Apple d’un compte Pro jamais remplacé (B16.4) (backend · MyWeli Pro · site · documentation · 2026-11-27 — BACKLOG B16.4, décision 221).** Branche `docs/spec-b16-4-auth-twin`, créée depuis `main` (`b097e330`). Spec : [auth-store-twins.md](../../design/auth-store-twins.md). Documentation seule : aucun code.
  - **Ce que l’étude avait lu, sans sonde :** quatre écarts entre le double en mémoire et Postgres dans les deux magasins de connexion (B-P1-a, B-P1-b, B-P2-b, B-P2-c).
  - **Ce que la sonde a montré** (une sonde jetable sur les deux doubles, une base locale jetable, supprimées après), avec un témoin par groupe :
    - **le lien Pro :** sur les deux doubles, un second compte Google qui affirme l’adresse vérifiée d’un compte Pro y entre. Postgres remplace le lien du compte, le double en ajoute un. La décision 260 ne l’arrêtait que pour les comptes clients : c’est un comportement de production, pas seulement un écart ;
    - **le code d’inscription Pro :** sur une adresse déjà prise, Postgres garde le code valide, le double le dépense. À côté, en production : deux inscriptions en vol sur une adresse lèvent une violation d’unicité, donc un 500 (2 essais sur 3) ; T35 dit « atomiquement » ; et des essais faux envoyés ensemble ne coûtent qu’un essai à eux tous (lu) ;
    - **les comptes Pro plus anciens que la refonte** gardent leur adresse non prouvée, et les deux recherches Pro par adresse l’ignorent : le piège de B16.3 pour Pro, si une telle ligne existe ;
    - **les comptes clients :** déjà d’accord depuis B16.3a ; un cas ajouté (une connexion sans adresse) ;
    - **la liste des utilisateurs de la console :** la plus récente d’abord dans Postgres, la plus ancienne dans le double ; `q=_` y liste tout le monde.
  - **La conception proposée :**
    - un lien Google ou Apple d’un compte Pro jamais remplacé : refus `409 social_link_taken`, avec une phrase dans l’application Pro et sur le site qui renvoie au code par e-mail ;
    - chaque code Pro vérifié sous le verrou de sa ligne, dans la transaction qui le dépense, comme le fait B16.3a construit : une inscription refusée garde son code, une course perdue répond `provider_exists`, plus jamais 500, et chaque essai faux compte ;
    - une règle de liste sur les deux doubles : la plus récente d’abord, une égalité tranchée par l’identifiant, chaque champ cherché seul, `%` et `_` pris tels quels ;
    - des contrats sur les deux doubles, rouges d’abord, des courses forcées sur Postgres seul, et quinze mutations ; T32, T33 et T35 corrigés.
  - **Relue une fois par un lecteur indépendant, chargé de la réfuter contre le code :** trois bloquants, chacun relu dans le code puis intégré. La première version copiait la conception de B16.3a, que sa construction avait abandonnée ; elle prédisait mal la réponse de la requête perdante ; et son test de course ne pouvait pas virer au rouge.
  - **Cinq questions** (décisions 284–288) : la règle du lien, le code, la liste, une lecture de production en lecture seule avant le déploiement, et l’ordre — une P2 en trois PR (le backend, puis la phrase de l’application Pro et celle du site), le déploiement du backend une fois celle du site en ligne et la lecture propre.
